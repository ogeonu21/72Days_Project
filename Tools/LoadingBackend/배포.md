# 로딩 서버 배포

현재 상태: 기존 데이터 서버는 사용자가 제공한 doGet의 헤더 규칙에 맞춰 StoryVersion을 3행 헤더/4행 값으로 수정한 뒤 정상 응답한다. 실제 원격5개 시트에서 67노드 런타임 카탈로그 구성을 Edit Mode에서 확인했다. 사용자가 doPost 배포를 갱신하여 실제 전송 성공과 같은 ID 중복 차단을 확인했다. 보안 후속 보완이 포함된 소스를 적용하려면 다시 새 버전을 배포해야 한다. 로딩 실패를 무시하거나 번들 데이터로 자동 진행하지 않는다.

1. Google Apps Script에 독립 프로젝트를 만들고 Code.gs와 appsscript.json을 적용한다. 기존 데이터 서버를 덮어쓰지 않는다.
2. 실행 계정은 72Days_DataSheet 읽기 및 72Days_ErrorReports_Temp 쓰기 권한이 있어야 한다. Google 권한 승인은 계정 소유자가 수행한다.
3. 웹 앱으로 배포한다. 소유자로 실행하며 게임 클라이언트에서 접근 가능한 수신점이 필요하다. 공개 수신점에는 코드의 일별500건 제한·4KB 크기 제한·입력 검증·오류 ID 중복 차단을 유지한다. 배포 권한과 공개 접근 여부는 소유자가 확인한다.
4. 배포된 HTTPS /exec 주소를 Unity의 Assets/Resources/LoadingSettings.asset의 reportEndpoint에 넣는다. 새 읽기 서버까지 사용할 때만 dataEndpoint도 바꾼다. 배포 URL 이외의 OAuth 토큰이나 비밀키를 앱에 넣지 않는다.
5. sheetName=StoryVersion 응답이 storyVersion/startNodeId가 있는 한 행인지 확인하고 NodeData/EventData/EventChoiceData/RewardData도 확인한다.
6. 오류 전송 버튼으로 테스트 보고서를 전송한 뒤 ErrorReports 시트의 ErrorId/OccurredAtUtc/Message 기록과 같은 ID 재전송 중복 차단을 확인한다. 기존 배포본의 실제 전송 한 건과 같은 ID 재전송 중복 차단은 확인했다. 후속 보안 수정본은 재배포 후 다시 확인한다.

스토리 내용·연결을 배포할 때 StoryVersion의 storyVersion도 반드시 변경한다. 필드 순서는 storyVersion/startNodeId이며 현재 헤더3행/값4행이다. 기존 세이브에 storyVersion이 없거나 새 버전과 다르면 이어하기가 거부된다. 저장 파일은 자동 삭제하지 않는다.

게임 시작은 빌드 목록 첫 번째 LoadingScene이다. MainWindow를 직접 여는 Editor 실행은 네트워크 로딩을 우회하는 개발용 경로다. Play Mode의 로딩→버전 경고→MainWindow 전환은 확인했다. 새 게임·이어하기·실제 저장 파일 쓰기·기기 빌드는 실행하지 않았다.
